## 0. 프로젝트 개요와 확정 사항

### 0-1. 목표

MY DESK는 Windows 바탕화면과 비슷한 사용 경험을 제공하는 개인용 통합 데스크톱 환경이다. 하나의 메인 화면에서 독립적으로 개발한 여러 도구를 실행하고 관리한다. 운영체제를 대체하지 않으며 Windows에서 실행되는 하나의 애플리케이션이다.

### 0-2. 확정된 기본 환경

| 항목 | 결정 |
|---|---|
| 운영체제 | Windows 11 (64비트) |
| CPU | AMD Ryzen 7 7800X3D |
| GPU | NVIDIA GeForce RTX 3060 12GB |
| RAM | 16GB |
| 여유 저장 공간 | 약 200GB |
| 개발 PC 인터넷 | 사용하지 않음 |
| 인터넷 가능 기기 | 학교 Chromebook |
| 파일 전달 | USB 메모리 |
| 화면 테마 | 다크 테마 + 배경 투시형 글래스모피즘 |
| UI 방향 | 익숙한 Windows 스타일의 데스크톱형 화면 |
| 화면 구성 | 아이콘, 작업 표시줄, 실행기, 이동·크기 조절 가능한 앱 창 |
| 확장성 | 기본 8개 모듈 외에 나중에 모듈 추가 가능 |
| 개발 보조 | Claude Code가 코드 작성·수정·테스트를 보조 |

위 사양은 설계 참고용이며 성능을 보장하지 않는다. 특히 AI·음성 기능은 메모리·GPU 상황에 따라 선택적으로 켤 수 있어야 한다.

### 0-3. 기본 모듈 8개

| # | 모듈 | 코드 위치(예정) | 개발 단계 |
|---|---|---|---|
| 1 | 파일 관리자 | `modules/file_manager` | 9단계 |
| 2 | 지식 관리자 | `modules/knowledge` | 8단계 |
| 3 | 자동화 도구 | `modules/automation` | 11단계 |
| 4 | 시스템 모니터 | `modules/system_monitor` | 10단계 |
| 5 | 도구 상자 | `modules/toolbox` | 7단계 |
| 6 | 시뮬레이션 실험실 | `modules/simulator` | 12단계 |
| 7 | 로컬 AI 비서 | `modules/assistant` | 13·14단계 |
| 8 | 통합 런처 | `shell/launcher` | 6단계 |

### 0-4. 제안 기술 구성 — 구현 전 호환성 확인 필요

| 영역 | 우선 검토 기술 | 확인할 사항 |
|---|---|---|
| 프로그래밍 언어 | Python | Windows용 설치 파일과 패키지를 오프라인으로 확보 가능한지 |
| GUI | PySide6 | 창·메뉴·위젯·다크 테마, 투명 창 지원 |
| 데이터베이스 | SQLite | 별도 서버 없이 로컬 저장 |
| 설정 파일 | JSON 또는 TOML | 사람이 읽고 백업하기 쉬운 형식 |
| 로컬 AI 실행 | llama.cpp 계열 | 모델·런타임은 별도 단계에서 검증 |
| AI 모델 형식 | GGUF 우선 검토 | 모델별 라이선스·용량 |
| 음성 인식(STT) | 오프라인 후보 비교 | 한국어 인식률, 설치 의존성 |
| 음성 합성(TTS) | 오프라인 후보 비교 | 한국어 음성, 사용 조건 |
| 호출어 감지 | 오프라인 Wake Word 후보 비교 | 마이크 상시 대기 부하, 오탐률 |
| 배포 | PyInstaller 등 | Windows PC에서 빌드·검증 |

위 기술은 최종 확정이 아니다. Claude Code가 임의로 기술을 바꾸지 않도록 하고, 패키지 호환성·오프라인 설치 가능성·라이선스를 확인한 뒤 확정한다.

## 2. 0단계 — 프로젝트 기준과 작업 규칙

### 2-1. 프로젝트 폴더 위치

Windows PC에 작업용 폴더를 만든다. 개발 폴더와 실제 사용자 데이터 폴더는 분리한다.

```text
D:\MY_DESK_DEV\
├── MY_DESK\              # 소스 코드 저장소
├── Offline_Installers\   # 설치 프로그램 보관
├── Offline_Wheels\       # Python 패키지(wheel) 파일
├── Offline_Models\       # AI 모델·음성 모델
├── USB_Staging\          # USB 전달 파일 임시 정리
├── Build_Output\         # 빌드 결과물
├── Test_Reports\         # 테스트 결과
└── Backups\              # 프로젝트 백업
```

실제 경로는 PC의 드라이브 구성에 맞춰 바꿔도 된다. 경로를 바꾸면 문서와 설정도 함께 갱신한다.

### 2-2. 파일·폴더 명명 규칙

- 폴더명과 코드 식별자는 일관된 영문 이름을 사용한다.
- 사용자에게 보이는 화면 문구는 한국어를 기본으로 한다.
- 파일명에는 날짜와 버전을 붙일 수 있다.
- 임시 파일은 `temp` 또는 `staging` 폴더에 두고 정리한다.
- 원본 설치 파일은 검증 전에 삭제하지 않는다.
- 모델 파일은 이름·버전·출처·라이선스·SHA-256 해시를 기록한다.

### 2-3. Claude Code 작업 원칙

Claude Code는 프로젝트의 구현 보조자다. 다음 규칙을 프로젝트 지침 파일(`CLAUDE.md`)에 넣는다.

**작업 방식**

1. 작업 전에 현재 폴더 구조와 관련 코드를 먼저 확인한다.
2. 요청받은 범위만 수정한다. 관련 없는 파일을 대규모로 재작성하지 않는다.
3. 기존 기능을 제거하거나 동작을 바꾸기 전에 이유와 영향을 설명한다.
4. 새 라이브러리를 추가하기 전에 패키지명, 버전, 라이선스, 오프라인 설치 방법을 보고한다.
5. 기능 구현 후 실행 가능한 테스트를 추가하고 실제 실행 결과를 보고한다.
6. 오류가 발생하면 원인, 재현 방법, 수정 파일, 검증 결과를 구분해 보고한다.
7. 테스트하지 않은 항목을 완료했다고 표시하지 않는다.

**오프라인·안전**

8. 인터넷 연결을 전제로 하는 코드나 런타임 다운로드를 추가하지 않는다.
9. 모든 기능은 인터넷이 끊긴 상태에서도 동작해야 한다. 온라인 기능이 불가피하면 선택 기능으로 분리하고 오프라인 대체 동작을 제공한다.
10. 파일 삭제·덮어쓰기·이동, 시스템 설정 변경은 기본적으로 미리보기와 사용자 확인을 거친다.
11. 비밀번호, 토큰, 개인 경로 등 민감한 정보를 코드나 로그에 기록하지 않는다.

**구조**

12. 모듈 간 직접 의존을 최소화하고 공통 기능은 Core 서비스를 사용한다.
13. 설정·데이터 파일의 형식을 바꾸면 마이그레이션과 백업 방법을 함께 제공한다.

**UI·디자인**

14. UI는 다크 테마·한국어·글래스모피즘을 기본으로 한다. 패널은 반투명 유리 재질로 만들고, 가능하면 실제 Windows 바탕화면이 뒤로 비치게 한다.
15. 배경을 임의의 풍경 이미지나 고정 그라데이션으로 대체하지 않는다. 사용자의 현재 Windows 배경화면을 우선 유지한다.
16. 투명도와 블러는 가독성을 해치지 않는 범위에서 적용하고, 텍스트·아이콘·상태 표시의 명암 대비를 확보한다.
17. Windows DWM 효과 등 운영체제 기능은 지원 여부를 런타임에 확인하고, 실패 시 대체 표현을 제공한다.

### 2-4. 작업 단위 보고 형식

Claude Code는 각 작업이 끝날 때 다음을 보고한다.

- 구현한 기능
- 수정·추가한 파일
- 새로 추가한 의존성
- 실행 방법
- 실행한 테스트와 결과
- 아직 해결하지 못한 문제
- 다음 작업 전에 사용자가 결정해야 할 사항

> **완료 조건:** 프로젝트 경로, 데이터 경로, 백업 경로, Claude Code 규칙이 정리되어 있다.

## 3. 1단계 — Chromebook에서 오프라인 개발 자료 준비

이 단계에서는 Windows PC에서 실행할 파일을 Chromebook으로 내려받아 USB에 보관한다. Chromebook에 Windows 프로그램을 설치하는 것이 아니다.

### 3-1. 먼저 확인할 항목

- [ ] Chromebook의 다운로드 공간
- [ ] USB 용량과 파일 시스템
- [ ] USB에 기존 중요 파일이 있는지
- [ ] USB 여유 공간 확보
- [ ] Windows PC가 64비트 Windows 11인지
- [ ] Python 버전 결정 전 PySide6·필수 패키지 호환성

## 6. 4단계 — 기본 데스크톱 화면

### 6-1. 확정 디자인 — 배경 투시형 글래스모피즘

메인 화면과 8개 모듈의 공통 디자인은 **배경 투시형 글래스모피즘**으로 통일한다. 사용자가 설정한 Windows 바탕화면이 MY DESK 뒤로 실제로 보이고, 그 위에 반투명 유리 패널·창·사이드바·작업 표시줄이 떠 있는 형태다.

#### 핵심 원칙

- 현재 Windows 바탕화면을 기본 배경으로 유지한다. 별도 풍경 이미지나 화려한 배경으로 덮지 않는다.
- 메인 셸 배경은 가능한 한 투명하게 두어 바탕화면이 빈 공간과 패널 뒤로 비치게 한다.
- 창·카드·사이드바·시작 메뉴·작업 표시줄은 반투명한 어두운 유리 재질로 표현한다.
- 패널 뒤에는 부드러운 배경 블러를, 가장자리에는 얇고 은은한 밝은 테두리를 둔다.
- 그림자와 하이라이트는 절제한다. 과도한 네온·강한 광택·장식용 그라데이션은 피한다.
- 기본 색상은 다크 네이비·차콜, 강조색은 차분한 블루 계열이다.
- 투명도는 장식보다 가독성을 우선한다. 긴 글·표·입력 폼은 충분한 불투명도를 확보한다.
- 텍스트와 아이콘은 한국어를 기본으로 하고, 아이콘만으로 기능을 추측해야 하는 상황을 피한다.
- 창의 이동·크기 조절·최소화·최대화·복원·닫기 등 기존 데스크톱 동작을 유지한다.
- 8개 모듈은 같은 모서리 곡률, 테두리, 블러, 그림자, 간격, 버튼 상태를 공유한다.

#### 실제 배경 투시 구현 방향

1. Windows 11 DWM(Desktop Window Manager) 배경 효과와 Qt/PySide6의 투명 창 기능을 조사해 적용한다. **창 투명도와 배경 블러는 별개 기능이므로 각각 검증한다.**
2. 메인 셸은 투명·반투명 창으로 구성하고 아이콘·위젯·패널만 필요한 영역에 그린다. 투명 영역을 불필요한 단색으로 채우지 않는다.
3. 패널 효과는 Acrylic/Mica 등 DWM 백드롭 계열을 우선 검토한다. 특정 Windows API에 의존하면 OS 빌드·GPU 드라이버·창 모드별 동작을 확인한다.
4. PySide6의 투명 배경 설정만으로 배경 블러가 자동으로 생긴다고 가정하지 않는다. 투명도·블러·그림자·클릭 입력 처리를 각각 시험한다.
5. DWM 블러를 쓸 수 없으면 사용자 바탕화면 이미지를 배경으로 쓰는 대체 모드를 검토한다. 이는 실제 투시가 아닌 이미지 기반 표현임을 구분하고, 바탕화면 변경 시 갱신 방법을 제공한다.
6. 투시 효과가 실패해도 검은 화면·흰 화면으로 깨지지 않도록 **단색 반투명 패널 모드**로 안전하게 전환한다.
7. 투명도와 블러 강도를 사용자가 조절할 수 있게 한다. 기본값은 배경이 분명히 비치되 글자가 편하게 읽히는 중간 수준이다.
8. 사용자의 Windows 배경화면 파일은 읽기 전용으로만 참조하고 수정·이동·삭제하지 않는다.

## 마지막 원칙

**한 번에 한 단계씩 진행한다.** 각 단계에서 다음 순서를 지킨다.

1. 해야 할 일을 확인한다.
2. 필요한 파일과 정보를 준비한다.
3. Claude Code에 작업 범위를 명확히 지시한다.

5. 구현한다.
